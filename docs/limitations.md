# Known limitations

- **RBAC is now enforced everywhere** (`app/auth.py`'s `require_role`, hierarchical `admin > operator > viewer`), applied per-endpoint across every router. `POST /api/jobs/run-command` and `POST /api/auth/register` are admin-only; day-to-day mutations (trigger jobs, promote/rollback, create resources) are operator-or-above; all `GET` list/detail endpoints are viewer-or-above. Verified live with three real users across representative endpoints per tier.
- **GPG signing is on by default** — `LifecycleEnvironmentCreate` requires `gpg_key_id` unless `allow_unsigned: true` is explicitly passed. See [`docs/gpg-signing.md`](gpg-signing.md). Key generation itself is still a manual one-time operator step (`gpg --full-generate-key`), not automated.
- **Both the API and published repos now serve HTTPS by default**, via a self-signed cert `install.sh`/`install-relay.sh` generate on first run. See [`docs/https.md`](https.md) for the trust-distribution mechanism (managed hosts get the CA cert pushed over the bootstrap SSH connection, not fetched over HTTP) and how to swap in a CA-issued cert.
- **Secrets remain a plaintext file** (`/etc/groundctl/groundctl.env`, `640 root:groundctl`) — no external vault integration. `docs/secrets.md` documents an opt-in `sops`/`age` encryption-at-rest wrapper around that file; it is not wired into `install.sh` automatically.
- **Per-host SSH keys are generated lazily, at bootstrap time, and only going forward.** `Server.ssh_key_path` is nullable; a host bootstrapped before this feature (or one whose bootstrap job never completed a keygen+install cycle) keeps using the shared fleet key indefinitely as fallback — there's no bulk migration/rotation for existing hosts. Compromising the shared key still compromises every not-yet-migrated host, plus the relay jump-hop (see below, unchanged in this phase). If a bootstrap run fails after generating a new keypair but before the key is confirmed installed, the next retry generates a fresh keypair rather than reusing the orphaned one — the old file is simply never referenced again, harmless but not cleaned up.
- **Rate limiting is narrow, not blanket.** Only `POST /api/auth/login`/`POST /api/auth/refresh` (5/minute), `POST /api/enrollment/register` (20/minute), and `GET /api/enrollment/script` (20/minute — see below) are limited — no other endpoint has any rate limit, and there's no account lockout after repeated failures (only the per-IP rate limit itself).
- **Refresh tokens have no server-side revoke-all-sessions endpoint.** `POST /api/auth/logout` revokes exactly the one refresh token presented; there's no "log out everywhere" that revokes every `RefreshToken` row for a user (e.g. after a suspected credential compromise) short of a direct DB operation.
- **Audit log retention (`audit_log_retention_days`, default 365) purges rows outright, with no special-casing for promotion-history reconstruction.** `rollback_environment`'s "which versions has this environment ever had live" check (Phase 1) reads `AuditLog` rows — if a version was last promoted more than a year ago and its audit rows have since been purged, rollback to that version will be rejected as never-live even though it once was. Extend the retention window if you need long-lived rollback history.
- **Automatic scheduling is a single global schedule, not per-resource.** Celery Beat runs `scheduled_sync_all_repositories` nightly (03:00) and `scheduled_compliance_scan` weekly (Sunday 04:00) against *every* repository/server — there's no way yet to exclude a specific repository from the nightly sync or run compliance scans on a different cadence per environment. On-demand triggering via the API still works as before for anything outside that schedule.
- **The stuck-job reaper only runs on API-process startup, not continuously.** A `Job` row orphaned by a worker crash is only caught the next time `groundctl.service`/the `groundctl` container restarts — it can sit at `status=running` indefinitely if the API process itself doesn't restart. Verified working (an orphaned job was correctly reaped on the next startup during this session's testing), but it's a one-shot check, not a background watchdog.
- **Job retry-exhaustion detection relies on `self.request.retries >= self.max_retries`, not `MaxRetriesExceededError`.** Celery's `autoretry_for` was found (empirically, against Celery 5.6) to re-raise the *original* exception on the final failed attempt rather than wrapping it in `MaxRetriesExceededError` as the docs might suggest — `app/tasks.py` handles this by checking the retry counter directly, with a `MaxRetriesExceededError` handler kept as a belt-and-suspenders fallback in case a future Celery version changes this behavior back.
- **`aptly api serve` has no authentication of its own** — it's bound to `127.0.0.1:8090` and reachable only by processes on the same host (`groundctl`, the Celery worker, and Beat all run as the `groundctl` system user there), which is the intended boundary. Don't expose port 8090 beyond loopback.
- **Async task handling in `aptly_client.py` is unverified against task-queue-style responses.** aptly's REST API has historically returned final results synchronously for these operations, but this has evolved across versions (see aptly's `task` subsystem). If large mirror syncs seem to return before they're actually done, this is the first place to look — add polling against `/api/tasks/:id` if needed for your aptly version.
- **`apply-updates` and `gather-facts` fan out to every matched server in a single Ansible run with default `forks`.** Fine for homelab-scale fleets; tune `ansible_runner.run(... forks=N)` if you're doing hundreds of hosts at once.
- **No migrations.** Tables are created with `Base.metadata.create_all()` on startup. Move to Alembic before this holds anything you'd be upset to lose on a schema change.
- **Package-drift compliance (`/api/compliance/servers/{id}/check`) compares against the environment's snapshot contents, not against upstream security advisories.** You get "is this out of date relative to what we've published," not CVE-level severity scoring. Use `/api/errata/{advisory_id}/affected-servers` for the latter — it's the same on-read comparison approach, but against USN/DSA package fix versions instead of the published snapshot.
- **Content view filters (`ContentViewFilter`, `AptlyClient.create_filtered_snapshot`) are less battle-tested than the rest of the aptly integration.** The request/response shape for aptly's `POST /api/snapshots/:name/filter` endpoint, and the translation from `ContentViewFilter.pattern` into aptly's own package-query syntax, follow aptly's documented contract but have not been exercised against a live instance the same way `?format=details` and the `Package`-vs-`Name` field naming were. If filtered publishes behave unexpectedly, this is the first place to look — verify the actual request/response shape against your aptly version before trusting it in production.
- **`AptlyClient.create_mirror` used to hardcode `Keyrings` to only the Debian and Ubuntu archive keyrings, which silently broke signature verification for any other signed archive** (found and fixed: the field replaces gpgv's default `trustedkeys.gpg` lookup rather than supplementing it). `create_mirror` now omits `Keyrings` entirely and relies on `trustedkeys.gpg` — import any additional archive's key there (see `scripts/lib/aptly.sh`'s `import_aptly_trustedkeys` for the existing Debian/Ubuntu import pattern) before mirroring it.
- **Errata have no usable severity field.** Neither the USN feed (`ubuntu.com/security/notices.json`) nor the DSA feed (`salsa.debian.org` security-tracker `data/DSA/list`) carries a severity rating in the data groundctl ingests — `Erratum.severity` exists as a column but is always `NULL` in practice for both sources today. Don't build a severity filter/dashboard against it as-is; it would just be grouping by `NULL`. The CVE IDs are already captured in `Erratum.cves`, so cross-referencing against NVD/CVSS later is the natural way to add real severity without a schema change.
- **The `errata_since` content view filter is the least-verified piece of the errata system.** Unlike `list_errata`/`affected-servers` (exercised end-to-end against real ingested USN/DSA data and a live FastAPI `TestClient` this session), `_errata_since_query` in `content_views.py` builds a `(Name (=...), Version (>=...)) | (...) | ...` aptly query that can chain many OR-clauses — one per affected package — and has **not** been run against a live aptly instance. This compounds the pre-existing unverified-query-shape caveat above for `include`/`exclude` filters with new, more complex query construction. If a content view using `errata_since` publishes emptier or larger than expected, check the actual query aptly received before trusting the result.
- **Errata ingestion is Beat-only — no manual trigger endpoint.** `ingest_usn_errata`/`ingest_dsa_errata` run on a fixed daily schedule (02:00/02:30, `celery_app.py`). If you need fresh errata data immediately after install (before the first scheduled run), invoke the Celery tasks directly rather than waiting, e.g. `celery -A app.celery_app call app.tasks.ingest_usn_errata`.
- **`POST /api/jobs/run-command` is as dangerous as SSH access to the fleet.** It runs the caller-supplied command string via `ansible.builtin.command` (no shell — shell metacharacters are rejected at the schema layer by `RunCommandRequest`, and even if they weren't, `command` never invokes a shell to interpret them) against every targeted host as `become: true` (root). Gated by real RBAC (see above) and fully audited — every invocation writes an `AuditLog` row with the exact command string and resolved target hostnames, in the same transaction as the `Job` row, *before* dispatch. There is still no undo, no dry-run, and no confirmation step. Treat activation-key issuance and run-command triggering as equally privileged operations.
- **Running an arbitrary named/uploaded playbook is explicitly out of scope**, not just deferred quietly. `run_command.yml` covers "arbitrary command"; `manage_package.yml`/`apply_updates.yml`/`bootstrap_client.yml`/`gather_facts.yml` cover the specific whitelisted operations groundctl knows how to run. Accepting an arbitrary playbook body/reference from a caller would let them specify `become`, loops, `delegate_to`, and any Ansible module — a materially larger and differently-shaped risk than one whitelisted command-execution task, and not something this phase attempts to safely constrain.
- **Self-registration (`POST /api/enrollment/register`) is intentionally unauthenticated.** The activation-key token *is* the authentication — same posture as `subscription-manager register --activationkey`. It's gated by token validity (hash lookup, revocation, expiry, use-count — all verified live) and rate-limited (20/minute per IP, see above) but not locked out after repeated failures. A leaked, unexpired, unrevoked activation key lets an attacker register arbitrary hosts into the referenced environment (and, if bootstrapped afterward by an operator, gives that rogue host the environment's apt sources). Treat activation key tokens with the same care as a password — revoke immediately if one is suspected leaked.
- **`GET /api/enrollment/script` raises the stakes on a leaked activation key.** The generated script (also gated only by the token, same as `/enrollment/register` above) doesn't just create a `Server` row — it also installs groundctl's shared fleet SSH public key into `/root/.ssh/authorized_keys` on whatever host it's run on. A leaked token lets an attacker run this against a host *they already control* to get that host tracked as a legitimate `Server`, or — more seriously — run it against a host they've merely compromised enough to execute one command on, granting the control plane's fleet key standing SSH access there. `GET /api/enrollment/ssh-public-key` itself is intentionally public (a public key isn't a secret), but the token that drives the rest of the script is; revoke immediately if suspected leaked, same as above.
- **Package search across the fleet (`GET /api/compliance/packages/search`) is an N+1 query over `Server` rows**, matching `errata.py`'s existing `affected-servers` pattern for consistency — not a normalized indexed table. Fine at homelab/small-fleet scale; if this becomes slow past a few hundred hosts, the fix is a normalized `ServerFactPackage`-style child table (mirroring `ErratumPackage`'s shape) written alongside `ComplianceRecord` in `gather_facts_task` — deliberately not built now since it doubles the write path for a query that's still fast at current scale.
- **"Last check-in" (`Server.last_seen_at`) only updates on a successful groundctl-triggered job** (bootstrap, apply-updates, gather-facts, bulk-apply-updates, run-command, manage-package) or self-registration. It is not a heartbeat — a host groundctl simply hasn't run anything against recently looks identical to one that's actually down until the next job targets it.
- **Webhook alerting is fire-and-forget with no retry queue.** `app/webhooks.py`'s `send_webhook` catches and logs delivery failures (timeout, non-2xx, connection error) but never retries — a down or misconfigured `webhook_url` silently misses events until the next event naturally fires again (e.g. the next day's staleness sweep). Set `webhook_url`/`webhook_secret` in `install.env` to enable; unset, alerting is still fully queryable via `AuditLog` rows (`flag_stale_server`, `mark_server_unreachable`) even with no webhook configured.
- **Host groups never retroactively change an existing server's `environment_id`.** `HostGroup.default_environment_id` is inherited only by a *new* server at the moment it self-registers via an activation key referencing that group (verified live). Adding an existing server to a group, or changing a group's `default_environment_id` afterward, never mutates that server's own `environment_id`. There is no `PATCH /api/servers/{id}` in this phase — reassigning an existing host's environment isn't exposed as an endpoint yet.
- **`_run_locked_job_multi`'s per-server lock acquisition is fail-fast and non-atomic across servers** (verified live against real Redis): if a job targeting 5 hosts acquires locks for 3 and then fails to acquire the 4th, the first 3 are released and the whole job fails immediately — matching the existing single-lock fail-fast posture, but meaning a large group/ad-hoc job is more likely to fail outright under contention than a single-server job. Retry once the conflicting job completes.
- **`ansible_runner_utils.run_playbook`'s fact-capture used to overwrite, not merge, `ansible_facts` across multiple `runner_on_ok` events in the same playbook run** — found live once `gather_facts.yml` grew from one fact-gathering task (`package_facts`) to three (`package_facts` + `setup` + `service_facts`): only the *last* task's facts survived, silently dropping the rest. Fixed by merging (`facts_by_host.setdefault(host, {}).update(facts)`) instead of assigning. Note for anyone adding a fourth fact-gathering task: `ansible.builtin.setup`'s output keys are `ansible_`-prefixed (`ansible_distribution`, `ansible_kernel`, `ansible_mounts`, ...); `package_facts`/`service_facts` land bare (`packages`, `services`) — `gather_facts_task` in `app/tasks.py` reads both conventions correctly, verified against a real target.
- **One relay per site, no multi-hop chains.** `Relay.site_id` is unique — no multi-relay load-balancing/HA within a site, and a relay is never itself routed through another relay. See [`docs/relays.md`](relays.md).
- **Relay sync is scheduled (hourly), not promotion-triggered — eventually consistent, not immediate.** A promoted (environment, content view) assignment reaches its relays on the next `scheduled_sync_relays` run, not the moment `POST /api/lifecycle-environments/{id}/content-views/{content_view_id}/promote` returns. Deliberate: aptly's own publish call can already take up to 1800s, and coupling relay sync into that request would make an already-slow endpoint slower and more failure-prone per relay. A relay being down or slow never blocks or fails a primary promotion.
- **ProxyJump and relay rsync still reuse the single shared fleet SSH key for the jump hop itself** — per-host keys (this phase) apply to the final hop to a fleet `Server`, not to a `Relay`, which remains infrastructure using the shared key. A relay only needs that one public key authorized for its `groundctl-sync` user; compromising the shared key compromises jump-routing through every relay, same blast radius as compromising it already had for direct fleet SSH access.
- **`ansible.posix.synchronize`'s SSH auth needed an explicit fix during live verification.** The module doesn't automatically inherit the inventory's `ansible_ssh_private_key_file` for its own rsync subprocess — `sync_relay.yml` passes it via the module's `private_key` parameter. Also: passing `-i <path> -o ...` through `rsync_opts` (a list of separately-passed argv items, not shell-parsed) breaks `--rsh`'s expected single-value parsing — use the dedicated module parameters (`private_key`, `delete`) instead of hand-building `rsync_opts` flags that need to stay together as one argument.
- **The bare `-o ProxyJump=` SSH option does not propagate `StrictHostKeyChecking` to its own implicit inner hop** (jump-host → final destination) — found live: a ProxyJump connection to a freshly-provisioned relay/behind-host pair failed host-key verification even with `StrictHostKeyChecking=accept-new` set on the outer connection, because that flag only applies to the outer (primary→relay) hop, not the one the `ProxyJump` shorthand spawns internally on the relay's behalf. Fixed by using an explicit `ProxyCommand=ssh -i <key> -W %h:%p -o StrictHostKeyChecking=accept-new <relay>` instead of the `ProxyJump=` shorthand, so the inner hop's flags are stated directly. If you see `Host key verification failed` / `Connection closed by remote host` errors routing through a relay for the first time, this is almost certainly why.
- **Relay content routing now has TLS (self-signed by default, same as the primary) but still no auth on its own nginx** — the served content is unauthenticated static files, same posture as the primary's published repos. `Relay.hostname` has no separate port field, so `_resolve_published_base_url` assumes the relay's nginx is reachable at the bare hostname on its default port — a relay installed with a non-default `--nginx-port` needs that reflected in the `hostname` value itself. A relay's `groundctl-sync` SSH user has no shell login and only owns the content directory tree, limiting blast radius if that account is compromised.
- **`Relay.content_size_bytes`/sync-lag monitoring is pull-based (computed at sync time via `du -sb`), not a continuous relay-side metric.** Between scheduled syncs, `Relay` row state reflects the last successful sync, not real-time relay disk usage.
- **`ansible.posix.authorized_key` (2.2.2) fails unconditionally in playbook execution mode on some ansible-core/Python combinations** — reproduced live as `Module failed: list index out of range`, with zero traceback, regardless of `become`, `manage_dir`, or any other option; the exact same operation via `ansible <host> -m ansible.posix.authorized_key` (ad-hoc mode) succeeds. `bootstrap_client.yml`'s per-host-key install task uses `ansible.builtin.lineinfile` against `authorized_keys` directly instead (a builtin, no collection dependency, and confirmed working both via direct SSH login with the newly-installed key and via a fresh-container end-to-end run). If you see this exact error from a different task using `ansible.posix.authorized_key` elsewhere, this is a known-bad combination, not a groundctl-specific bug.
- **A `LifecycleEnvironmentCreate.allow_unsigned` validator gap was found and fixed during live verification**: pydantic v2 skips `@field_validator` entirely for a field left at its default value unless `validate_default=True` is set on that field — since `allow_unsigned` defaults to `False` and is normally omitted from the request body (the exact case the check exists for), the "gpg_key_id required unless allow_unsigned=true" validation never actually ran until this was added. Worth remembering for any other validator that depends on a field's default value rather than an explicitly-supplied one.
- **CI's mypy job is non-blocking (`continue-on-error: true`).** This codebase had zero prior type-check history before Phase 7 — a hard-fail gate on day one would block on pre-existing code, not new regressions. Tighten this once the existing codebase is reasonably clean; until then, `mypy` failures are visible in CI output but don't fail the build.
- **`/metrics` does not proxy or aggregate aptly's own metrics** (if its version exposes any) — matches CLAUDE.md's rule against forwarding arbitrary aptly calls through this app. Operators wanting aptly-level metrics scrape aptly directly; since it's loopback-only and unauthenticated, this requires an explicit operator decision (e.g. an SSH tunnel or a sidecar), not something groundctl defaults to. See `docs/metrics.md`.
- **`scripts/backup.sh` is a full-dump procedure, not point-in-time recovery.** `pg_dump`/`pg_restore` plus a `tar` of `/var/lib/groundctl` — recovery granularity is "as of the last backup run," not "as of any specific moment." If you need sub-daily RPO, set up WAL archiving/`pg_basebackup` separately; see `docs/backup.md`.
- **Structured log lines from Celery tasks carry `correlation_id: null`.** `app/logging_config.py`'s correlation-ID contextvar is set by `CorrelationIdMiddleware` for the lifetime of an HTTP request; Celery tasks run in a separate worker process outside that request context, so there's no way to trace a job dispatch (which does have a correlation ID, from the triggering API request) through to its eventual Celery execution's own log lines. A real gap, not addressed in this pass — would need the correlation ID threaded through as an explicit Celery task argument (e.g. alongside `job_id`) to close.
- **`GET /health` is not wired into systemd's own service-gating** (no `ExecStartPre` health check on `groundctl.service`). `Restart=on-failure` already handles process-level liveness; adding a pre-start dependency check would slow every restart, including transient ones that don't need it. The endpoint is meant for external monitoring (Prometheus's own `up`/blackbox-exporter-style checks, or a manual `curl`), not for gating systemd's own start/restart behavior.
- **Alembic's baseline migration (`0001_initial`) captures the schema as of Phase 7, not real incremental history.** There was no prior migration history to reconstruct — every phase through Phase 6 used `Base.metadata.create_all()`. Confirmed byte-for-byte identical (`pg_dump --schema-only` diff) against a fresh `create_all()`-produced schema before being adopted as the baseline. All schema changes from Phase 8 onward must go through a real `alembic revision --autogenerate` migration — do not add a column/table directly to `app/models.py` without one.
- **Uploaded logo/favicon images are validated only by MIME type and a 2 MB size cap** (`app/routers/branding.py`) — not decoded/re-encoded, so no dimension check, no malformed-file rejection beyond what the browser's own `Content-Type` sniffing reports, and no protection against a technically-valid-but-absurd image (e.g. a 1px-tall PNG stretched across a 10000px canvas) rendering oddly in the sidebar/browser tab. SVG is deliberately excluded (script/event-handler injection risk — see the router's own comment), which covers the actual security-relevant gap; the rest is a display-quality concern an admin self-inflicts, not something another user's input can trigger.
- **No way to clear a customized logo/favicon/color back to the built-in default from the UI.** `PUT /api/branding/colors` accepts `null` to explicitly clear a color (the API supports it), but the Appearance screen has no "reset" button wired to it, and there's no equivalent clear path for an uploaded logo/favicon at all (`Branding.logo_data`/`favicon_data` can only be overwritten with a new upload, never nulled out) — once uploaded, only replacing with a different image removes the old one, not un-setting it entirely.
- **No admin-driven password reset for other users.** `PUT /api/auth/me/password` is self-service only (requires the current password) — if a user forgets their password, the only path today is an admin creating a *replacement* account or the same manual direct-DB escape hatch `docs/quickstart.md` documents for a lost first-admin password. Deactivating and reactivating a user does not touch their password.
- **`GET /api/branding`, `/branding/logo`, and `/branding/favicon` are all unauthenticated** — deliberate (the login screen and browser tab need to render custom branding before any session exists, same reasoning as `GET /api/enrollment/ssh-public-key`), but means anyone who can reach the API at all (not just authenticated users) can read the configured colors and download the logo/favicon images. Never put anything sensitive in a color value or image — there is no way to scope these to authenticated users without also breaking the pre-login use case they exist for.
- **Environment reassignment (`POST /api/servers/{id}/assign-environment`, Phase 9) only changes the database row.** Getting the change onto the actual host still requires a separate, explicit `POST /api/jobs/bootstrap/{id}` (SSH/Ansible) until the Beacon agent's checkin-based reconciliation ships — until then, a reassigned server keeps serving its old environment's packages indefinitely if nobody re-bootstraps it. `bootstrap_client.yml` does correctly remove the previous environment's `sources.list`/keyring on that re-run (a content host trusts exactly one groundctl-managed environment at a time), so the re-bootstrap step itself is safe to run repeatedly — it just isn't automatic yet.
